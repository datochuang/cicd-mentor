# 標題盲讀審稿：《互動場景》（2026-10-09）

**做法**：同前幾次。讀者設定為 PL 或資深工程師，可能會和 agent 打交道，不知道「PM」在這裡指誰。

**處理**：
- 採用：「patch」全部改成 shelved CL（Perforce 沒有 patch 這個詞）；PM 在第 1 頁用語裡定義為「推動 CI/CD 的那位技術主管」；PROJECT_MAP、狀態板、subagent、shelved CL 在第 1 頁各一句定義；第 2 頁補上「權限分階段：先只讀，要交 shelved CL 時加寫入，要開 stream 時再加，每一階 PM 給」，解掉只讀上線和代開 stream 的矛盾；第 11 頁的歧義句「拒絕交 PM 決定」改成「被拒絕由 PM 裁決」；「擱置」改「延後」，「當眾」改「在同一個 channel」；「情勢判斷」改「盤點」、「掃整個 depot」改「掃指定的 depot 範圍」；「看守」全改「監看」；「退場」與「退到看守」的矛盾改成「交棒：團隊能自己維護後 agent 只剩監看」；「請准」改「核准」；透明與延後／誤報兩頁移到最後並以「橫跨全程」開頭，不再被讀成時間線的步驟；第 8 頁「什麼時候」註明是第一道 check 上線之後的常態。
- 未採用：把「狀態板」「PROJECT_MAP」改成別的名字（這兩個是本專案的產物名，定義過即可）。
- 沒處理：第 4 頁的 owner 是 block owner 還是 CL owner——目前兩頁都指 block／目錄的 owner，日常監看頁找的是 CL 的作者；內文已分別寫明，標題不再加字。

## 原始報告（subagent 的話，逐字）

### A. 只看文件標題

**講什麼、給誰看、讀完要做什麼**

- 講什麼：看得出是「一個 AI agent 進來之後，跟人和 repo 怎麼互動」的流程描述。但標題本身是一整句話塞三個主詞（agent、PM、團隊），讀起來像摘要句而不是標題，第一眼抓不到重點。
- 給誰看：標題沒說。kicker 列了 PM、團隊、repo，所以我猜是給「會被 agent 打擾的人」看的，也就是我。但也可能是給管理層看的決策文件，兩種讀法都通。
- 讀完要做什麼：完全不知道。是要我同意這個流程？要我知道自己哪一步會被問？還是要我去設定 Perforce 權限？標題沒有任何「行動」的暗示。

**四個詞我會怎麼理解**

| 詞 | 我的第一反應 | 問題 |
|---|---|---|
| PM | 專案經理（排 tapeout schedule、追進度的那位） | 我們公司的 PM 不管技術方向，更不會核准 CI/CD 的 check 設計。標題說「方向由 PM 核准」，我會直接懷疑這份文件是不是搞錯對象，或者這個 PM 其實是指某個技術主管。整份文件沒有一頁定義 PM 是誰。 |
| agent | 驗證工程師第一反應是 UVM agent；做 build 的人會想到 Jenkins agent（build node） | 整份文件把它當專有名詞用卻沒定義。「agent 以 bot 身分上線」才讓我確定是某種自動程式，但那是第 2 頁。 |
| patch | git diff 或一個 .patch 檔用 mail 傳來傳去 | Perforce 沒有 patch 這個概念。我們交東西是 shelved CL。第 6 頁自己就用了 shelved CL，標題卻用 patch，兩套詞混用會讓我覺得寫的人不熟 Perforce。 |
| owner | 「這個 block 的 owner」，這在 IC 公司是日常用語，可以懂 | 但 CL 也有 owner（submitter）。第 4 頁「私訊 owner」我會猜是 block owner，第 8 頁「CL 進來」之後沒說找誰，我會猜 CL owner。文件沒分清楚這兩種 owner 是不是同一個人。 |

另外「採不採用團隊決定」：採用什麼？agent 本身？agent 交的 CL？CI/CD 這整套？三種讀法都成立，而答案會決定我要不要緊張。

### B. 十二個標題連起來的邏輯

看得出 2 到 7 是一條時間線：上線 → 掃描 → 選目標 → 深入分析 → 核准 → 建置 → 分級上線。這段順序合理，而且 7 是整份文件最像 Perforce 人寫的一頁（report / warn / block submit / bypass）。

斷點有三個：

1. **7 → 8 之間斷掉**。前面是「做出第一道 check」的一次性流程，8 突然變成「每天看 CL」的常態。沒有一頁說明「第一道 check 上線之後，agent 的工作模式就切換了」，讀者會以為 8 還在時間線上。
2. **9「開工輔導」完全不知道接在哪裡**。開什麼工？新 block？新 project？新 tapeout？「看到跡象」是什麼跡象？這一頁夾在日常看守和透明之間，像另一份文件的內容掉進來。
3. **10、11 是原則不是場景**。透明、擱置與誤報，是橫跨所有階段的規則，放在時間線末端會讓人以為「做到第 10 步才要透明」。

12 又跳回時間線（加下一道 check → 退場），而且「退場」和「退到看守」在同一個標題裡互相矛盾：到底是走了還是留著？

還有一個 Perforce 人一定會注意到的權限矛盾，從標題就看得出來：第 2 頁「只讀上線」，第 6 頁要 shelve CL（需要寫入），第 9 頁要「把 stream 準備好」（stream 是 admin 等級的操作）。權限什麼時候、由誰升的，沒有一頁交代。

### 最需要改的前 5 個

1. **文件標題**：拆成「標題 + 副標」，把 PM 是誰、patch 換成 CL、「採不採用」的受詞補上。現在這句話是整份文件最難讀的一行。
2. **第 11 頁「拒絕交 PM 決定」**：歧義會導致相反理解，這是唯一會造成實際誤判的標題，必須加字或換句。
3. **第 9 頁「開工輔導」**：整頁目的看不出來，而且暗藏 stream 建立權限的問題，要麼改名說清楚開什麼工，要麼移到附錄。
4. **未定義的自創詞**：PROJECT_MAP（第 4 頁）、subagent（第 6 頁）、狀態板（第 9、10 頁）三個詞第一次出現就當讀者認識。至少在第 1 頁或第 2 頁各給一句話定義。
5. **「看守」與「PM」全篇統一**：「看守」出現在 1、8、12 頁，換成「監看」；「PM」在第 1 頁第一次出現時就括號註明是誰（技術主管？專案經理？），不然 IC 公司的讀者會從頭到尾帶著錯誤的人物設定讀完。
