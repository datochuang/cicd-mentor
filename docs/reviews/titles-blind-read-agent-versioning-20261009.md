## 原始報告（subagent 的話，逐字）

以下以「每天用 Perforce、聽過這個 agent 要被 clone 好幾份、沒看過任何其他文件」的資深工程師／CAD 身分，只看標題作答。

### A. 文件標題與 kicker

**這份文件講什麼**：講這個 AI agent 自己的程式碼放哪裡、怎麼改版、clone 成好幾份之後怎麼管。kicker「agent 自己的版控與多實例」把範圍講得比主標題清楚，主標題反而是三句結論硬塞在一起。

**給誰看**：猜是要接手做 agent 的人和 CAD。但標題看不出來讀完要做什麼：這三句是「已經定了，照做」還是「提案，請你決定」？看到第 10 頁「待決」才知道有一部分沒定。主標題應該帶出讀者的動作（例如「……三件待公司決定」）。

**五個詞的第一眼理解與誤會**：

- **core**：在 IC 公司這個字第一反應是 IP core／CPU core。「core 在 git 出 release」我第一眼讀成「IP core 改在 git 上 release」，會嚇一跳。要等到第 2 頁「core、instance 設定、目標的知識」才推出 core = agent 本體程式。建議直接寫「agent 本體」或「agent core 程式」。
- **實例**：中文「實例」平常是「實際案例」；工程師讀到 RTL 腦袋裡的 instance 是 module instantiation。第 1 頁「實例不改自己」我完全不知道主詞是什麼、「改自己」是改程式還是改設定。要到第 5 頁「一個路徑一個實例」才確定它是 clone 出來的那一份 agent。既然大家聽到的是「clone 成好幾個」，用「分身」或「每一份 agent」比「實例」好；至少第 1 頁要定義。
- **目標**：沒定義。目標是 build target？synthesis target？看完十頁推測是「agent 盯的那個 depot 路徑」，但第 5 頁叫「路徑」、第 7 頁叫「目標 repo」、標題叫「目標的 depot」，同一個東西三個名字。
- **目標的知識**：最不懂的詞。是「agent 對那個 depot 學到的東西」還是「那個專案本身的 know-how」？「知識留在目標的 depot」聽起來像「不要把專案 know-how 搬出去」，我猜真正意思是「agent 針對某 depot 累積的筆記就 submit 進那個 depot」。這兩種讀法差很多。
- **depot**：這個沒問題，Perforce 用語。但「core 在 git、知識在 depot」並列，馬上引出「為什麼 agent 的程式不放公司的 Perforce」這個問題，標題不回答，十頁裡也沒有一頁正面回答（第 9 頁有點像，但標題看不出來）。

### B. 十頁連起來的邏輯

**脊椎看不出來**。我自己排出來的結構是：1 總覽 → 2 放哪裡 → 3–4 core 怎麼改 → 5–6 多份怎麼管 → 7–8 守規矩與花錢 → 9 示範 → 10 待決。但標題上沒有任何標記告訴我「現在在哪一段」，第 7、8 頁為什麼接在版本後面也沒交代。

**斷掉的地方**：
- 第 6 頁「版本」跳到第 7 頁「安全」，中間沒有橋。安全頁的「規則只從 core 來」和版控有關係，但「目標 repo 裡的文字一律當資料」是另一件事（防止 agent 被 repo 裡的文字牽著走），從版控文件的角度讀不出為什麼在這裡。
- 第 8 頁「資源：預算、CAD、請准單、PM」完全不在 kicker「版控與多實例」的範圍，像是從一份「營運／費用」文件掉進來的。「預算以實例計」勉強沾到多實例，後半句「請准單與摘要彙整成一份給 PM」和版控毫無關係。
- 第 9 頁「示範」是獨立的一個點，不在前面任何線上，放在第 8 與第 10 之間很突兀。它其實是在回答 A 裡那個「為什麼 core 放 git」的問題（因為要當範本給人看），如果是這樣應該往前挪到第 2 頁附近。

**重複**：
- 第 1 頁就是主標題加三個字，資訊量為零。
- 「實例不改自己」在標題、第 1 頁、第 3 頁出現三次。
- 第 3 頁「過沙盒與 review 才出 tag」和第 4 頁「三件過才能 tag」講同一道關卡，第 4 頁應該只講沙盒長什麼樣，tag 的門檻留給第 3 頁。
- 第 6 頁「升級先 canary」和第 10 頁「升級的節奏」一個講升級方法、一個說升級節奏待定，讀起來像前面已經定了後面又說沒定。

**看起來矛盾的地方**：
- 主標題說 core 在 **git**，第 4 頁說 core 的 CI 是一個小 **depot**。我懂的話會猜「測試資料是 Perforce depot 因為被看的對象是 Perforce」，但不懂的人會覺得 core 到底在 git 還是 Perforce。
- 第 9 頁說「core 的 **repo**」，第 7 頁說「目標 **repo**」，主標題說「目標的 **depot**」。repo 在公司不是慣用字，而且同時拿來指 git 端和 Perforce 端，更亂。
- release（標題）、tag（第 3、4 頁）、版本（第 6 頁）三個詞指的是不是同一件事？在 git 裡 tag 和 release 幾乎同義，但標題不該讓讀者自己猜。
- 第 2 頁說三層，第 5 頁冒出「共用物」。共用物是第四層嗎？放哪裡？

### C. 逐頁

**1. 總覽**
- 猜：整份文件一頁講完。信心高（因為就是標題重抄）。
- 問題：和主標題完全相同，沒給讀者任何額外的東西，例如「這三句各對應哪幾頁」。core／實例／目標／知識四個詞在這頁就得先講白。
- 改寫：「總覽：agent 程式在 git 出版，各分身不自改，各 depot 的經驗存各自 depot」

**2. 三層**
- 猜：一張三個框的圖，各放哪裡、多久改一次。信心高。
- 問題：「instance 設定」突然用英文 instance，第 1 頁用中文「實例」，不統一。「目標的知識」仍不知道是誰的知識。「生命週期不同」好，但看不出具體差在哪（core 幾個月一版、設定隨時改、知識每天長？）。
- 改寫：「三層：agent 程式、每份的設定、每個 depot 的經驗，分開放、分開改」

**3. 進化**
- 猜：agent 怎麼變聰明：分身發現好做法 → 開 MR 回 core → 跑沙盒＋人 review → 打 tag → 大家升級。信心中高。
- 問題：「進化」太文藝，講「改版」就好。「學到的」是什麼東西？agent 學到的是 prompt？規則？程式？不知道走 MR 的是哪一種檔案。「不改自己」還是沒說清楚是不改程式還是不改設定。
- 改寫：「改版：分身不自改程式，改進一律開 core 的 MR，過沙盒和 review 才打 tag」

**4. 沙盒**
- 猜：一個人工做的小 Perforce depot，裡面埋了 16 種已知的壞樣本，每次 core 要出版就拿它跑一遍。信心中。
- 問題：「十六個症狀」是討論裡才有的數字和比喻，「症狀」聽起來像看病，盲讀猜不到是「depot 裡故意埋的問題樣本」。「偵測、提案、紅線」三件是什麼？偵測＝有抓到，提案＝有給建議，紅線＝沒做不該做的事？這是我硬猜的。「是 core 的 CI」這句好，但對 IC 讀者講「regression」更直覺。
- 改寫：「沙盒：埋了 16 種已知問題的小 depot 當 core 的 regression，三項全過才能 tag」（紅線三件最好在圖裡展開，不要在標題寫「三件」）

**5. 多實例**
- 猜：部署拓樸：每個被看的 depot 路徑配一份 agent；兩份都會碰到的東西指定一份負責；Slack 訊息和 shelved CL 都署名是哪一份發的。信心中高。
- 問題：「共用物」太抽象——是兩個路徑共用的 include 檔？共用的 Slack channel？共用的設定？「一個路徑」是 depot 路徑還是檔案系統路徑？「帶實例名」好懂。
- 改寫：「多份 agent：一個 depot 路徑一份，跨路徑共用的檔案指定一份負責，訊息與 CL 署名」

**6. 版本**
- 猜：版號規則與升級方式。信心中。
- 問題：「同一家公司同一個 major」最怪——我只在一家公司，為什麼標題要強調「同一家公司」？讀起來像這是要賣給好幾家公司的產品。「canary」是 web 部署用語，IC 工程師多半沒聽過；「major」多數人懂 semver 但不是全部。
- 改寫：「版本：訊息和 log 都標版號，全公司分身 major 一致，升級先挑一份試跑」

**7. 安全**
- 猜：agent 的行為規則只認 core 程式裡寫的，被看的 depot 裡的文字（註解、README、commit message）不能當命令；core 的 main branch 鎖起來只能走 MR。信心中低（前半句猜的）。
- 問題：「規則」在 Perforce 世界第一反應是 protect table 或 lint rule，不會想到是 agent 的行為規則。「一律當資料」看不出為什麼——要說「不能指揮 agent」才知道在防什麼。「目標 repo」在這裡又變 repo。
- 改寫：「安全：agent 只聽 core 的規則，被看 depot 裡的文字不能指揮它；core 的 main 鎖住」

**8. 資源**
- 猜：每份 agent 花多少（token？機器？錢？）各自計帳，總額 CAD 控管；各份要請示的事和每天的摘要合併成一份給 PM。信心低。
- 問題：「預算」是什麼單位完全看不出來。「請准單」不是公司用語（會說簽核、申請、請示）。「PM」在 IC 公司就是專案 PM，我沒看別的文件，不知道這裡的 PM 是「負責導入 CI/CD 的那個人」，會誤會成要把 agent 的事送給專案 PM 簽。「CAD」當部門讀沒問題。這頁一半講花費、一半講匯報，兩個主題，而且都不是版控。
- 改寫：「用量：token 費用一份一份算、總額 CAD 管；各份的請示合併一份給負責導入的 PM」（或整頁移出這份文件）

**9. 示範**
- 猜：core 自己的 git repo 就照 CI/CD 的做法經營，團隊想看 CI/CD 長什麼樣就看它。信心中。
- 問題：「六個原則」沒在任何標題出現過，盲讀無從得知；如果圖裡有六個膠囊那標題可以不寫數字。「自己守」的主詞是 repo 還是維護 core 的人？這頁其實回答了「為什麼 core 放 git」，但標題沒點出這個連結。
- 改寫：「示範：core 的 git repo 自己照 CI/CD 做，團隊要看範例就看它」

**10. 待決**
- 猜：三件事還沒定，要公司決定。信心高。
- 問題：「一實例一帳號」是 Perforce 帳號還是 Slack 帳號？猜 Perforce，但 agent 也上 Slack。「公司定」是誰定？CAD 主管？老闆？「升級的節奏」和第 6 頁「升級先 canary」要對齊——第 6 頁定了方法，第 10 頁說節奏沒定，標題上最好讓人看出這兩個是不同的事。
- 改寫：「待決：core 誰維護、每份 agent 用一個 Perforce 帳號還是共用、多久升級，三件待定」

### D. 最需要改的前 5

1. **core／實例／目標三個主角沒定義就上場，而且都和 IC 用語撞名。** core = IP core、實例 = RTL instance、目標 = build target，第一眼全會讀錯；要到第 2、5 頁才拼得出來。主標題和第 1 頁就要用不會撞的名字（agent 本體、分身、被看的 depot），或在第 1 頁一句話定義。
2. **「目標的知識」這句結論看不懂。** 它是主標題三分之一的主張，卻分不清是「agent 對那個 depot 學到的東西」還是「專案本身的 know-how」。改成「agent 對某個 depot 學到的事就 submit 進那個 depot」之類的直述。
3. **第 7、8 頁超出 kicker 的範圍，第 8 頁像別份文件掉進來。** 「預算、請准單、PM」和版控無關，而且「PM」在沒讀其他文件的人眼裡就是專案 PM。要嘛移出去，要嘛改 kicker 讓範圍涵蓋「怎麼養」；留下來的話 PM 要在標題裡講清楚是哪種 PM。
4. **只有討論參與者才知道的數字和簡稱：十六個症狀、六個原則、紅線、共用物、請准單。** 這些在標題裡盲讀全部猜不到；數字放進圖裡、標題改成說得出意思的詞（已知問題樣本、不可做的事、跨路徑共用的檔案）。
5. **同一個東西多個名字：release／tag／版本；git／repo／depot；目標／路徑／目標 repo／目標的 depot；實例／instance。** 加上第 6 頁「同一家公司」讓人以為這是外購產品。每組挑一個，全文只用那一個；公司端一律 depot，git 端一律 git。

附帶一點：第 1 頁與主標題完全相同、十頁沒有任何「你現在在哪一段」的標記，讀者停在第 1 頁拿到的是三句沒定義的口號，不是結論。

# 第二輪（同日，D5 與換手頁加入、檔名改成 agent-own-version-control-and-instances 之後）

**做法**：同第一輪，給檔名、文件標題、kicker、十一頁標題。

**處理**：
- 採用：
  - **master／main 衝突**（第 2 頁 master、第 7 頁 main）：全份統一 master。
  - **「生產用的工具」撞量產**：改成「流程在用的工具」「團隊流程裡真的在用的工具」；第 2 頁的判斷句改成「團隊的流程有沒有真的在用它」。顧問比喻那句保留「客戶生產線」，因為比喻本身已鋪過。

  - **「生出來」口語且和 clone 兩種說法**：標題與第 1 頁都改成 clone。

  - **頁序 core 與實例交錯**：改成 1 總覽 → 2 三層 → 3 為什麼 git → 4 改版 → 5 沙盒 → 6 安全（core）→ 7 多實例 → 8 換手 → 9 版號 → 10 代價（實例）→ 11 待決；第 1 頁底下寫明分段。
