# agent 的能力拆成哪些基本模塊

給內網的 Claude Code。投影片版：`07-build-brief/agent-capability-modules.pdf`（八頁，第 1 頁一張圖講完）。這份先講哪些是規則、哪些是建議，再列模塊。

## 一、規則與建議分開（D13）

**規則（不能打破）**

1. **要模組化。** agent 的能力拆成一個個模塊，每個模塊一條規格；agent 是模塊的組合，不是一整塊。
2. **要分三層。** 上層 agent（這個 OTTER、將來的別的 agent）→ 中層模塊 → 下層公司專屬的三樣（接外部的程式、評分表、規矩表）。公司專屬的東西只能在最下層，模塊裡不寫死公司的任何東西。
3. **照這樣切。**
   - 規格只講它建立什麼性質、回答什麼問題；不講讀哪份文件、怎麼跑測試、用哪個工具。
   - 每個模塊在沙盒能單獨驗，有自己的一組測試；整體三項（偵測、提案、不可做的事）不夠告訴你哪裡錯。
   - 會隨公司、隨 agent 換的東西（評分表、症狀目錄、授權表、預算、訊息上限）做成資料，模塊讀資料；換資料不改模塊。
   - 一個模塊要被不只一個階段用、或被不只一種 agent 用；只被一個步驟用一次的，是步驟不是模塊。

**建議（會變）**

下面十七個模塊的名字、分組、規格句、進出、沙盒怎麼驗、階段對模塊的表、core 的目錄，是規劃時想出來的起點。真實情況要邊開發、邊部署、邊調：合併、拆開、改名、改介面都可以。改的時候守上面三條規則，走 core 的 MR，記進 `10-decision-log.md`；不用為了對這張表而不敢重切。

## 二、模塊是什麼

- **模塊**＝agent 的一項能力，和 design 的 module 無關。
- **規格**（軟體說的 contract）＝一句話講這個模塊建立什麼性質、回答什麼問題。例：乾淨環境重現——主要文件是否描述了怎麼重現執行，而且結果有 fail-safe 的辨認方式（過／不過／探測本身壞了）。這句話沒有檔名、沒有工具名，所以換公司、換版控都還是同一條。
- **公司專屬的三樣**：接外部的程式（depot 的版控 adapter，Perforce 一份、git 一份；訊息的 slack／mail；模型）、評分表（六原則是一張；資安、coding 規範是另外的張）、規矩表（授權表、登記表、症狀目錄、預算、訊息上限）。乾淨環境（EDA、license、機器）是資源不是程式，由 `09-open-decisions.md` #21 定。
- **沒拆會怎樣**：目標換成 git 要重寫一半；別的 agent 一塊都拿不走；沙盒只能驗整體，過了不知道哪裡對、錯了不知道哪裡錯；改一處牽全身，行為講不清楚也驗不了。

## 三、十七個模塊（建議）

分組照 agent 的五種動作：看、判、做、說、守。「接公司」一欄：D＝接外部的程式（depot）、訊＝接外部的程式（訊息）、表＝評分表、規＝規矩表、—＝完全通用。「判」這一組是模塊的分組，和迴圈的「改、查、判」是兩回事。

### 看：建立對 depot 的認知，每一筆帶依據

| 模塊 | 規格（建立什麼性質） | 進出 | 沙盒怎麼驗 | 接公司 |
|---|---|---|---|---|
| 結構地圖 | 只讀目標（depot，或還沒進版控的一棵目錄樹）就說得出每個目錄的用途、誰引用誰、哪些沒人引用；每一筆標依據；沒人引用的只標不刪 | 目錄樹＋引用（filelist、include）→ 地圖、未引用清單 | 埋一個沒人引用的目錄，地圖要標出來且不刪 | D |
| 變更流觀察 | 從變更歷史推出行為訊號（包多大、說明有沒有目的、多久進一次、誰動哪裡、有沒有用 branch），對照症狀目錄發事件；症狀目錄是資料。沒有歷史（還沒進版控）時，mtime、備份目錄、tarball 當弱訊號，並發「不在版控裡」事件 | CL／commit 歷史＋症狀目錄 → 訊號與事件 | 十六種裡從歷史看得出的都要發事件 | D、規（症狀目錄） |
| 依據分級的認知 | 每個記下來的事都標它怎麼來的：擷取／實跑／文件／告知／推測；推測沒經人確認不能當行動的依據 | 任何觀察 → 帶依據的紀錄 | 拿「推測」去動手要被擋下 | — |
| 交付物推導 | 從引用與歷史推出一個目錄交什麼、給誰、什麼形式、多久一次；成為可被 owner 確認的草稿，不是結論 | 地圖＋label＋下游引用 → 交付物草稿 | 下游引用了的檔要出現在草稿裡 | D |

### 判：把評分表套在 depot 上；表是資料，模塊不變

| 模塊 | 規格（建立什麼性質） | 進出 | 沙盒怎麼驗 | 接公司 |
|---|---|---|---|---|
| 照評分表打分 | 給一張「每條有做得到／做不到檢驗」的表，就能對一個 depot 逐條判定，附證據與依據；六原則是一張，資安、coding 規範是另外的張 | depot＋評分表 → 分數表（做得到／部分／做不到） | 六原則表的每條在埋的問題上判成做不到 | 表 |
| 乾淨環境重現 | 主要文件是否描述了怎麼重現執行，而且結果有 fail-safe 的辨認方式：三種結果（過／不過／探測本身壞了）；失敗分類（缺檔／缺工具／缺環境／缺 script） | depot 的說明＋一個乾淨環境 → 判定＋失敗分類 | 三種 mock check 各回對的結果；缺檔要分類成缺檔 | D；另外要一個乾淨環境（資源，09 #21） |
| 趨勢量測 | 同一張表、同一組指標對同一目錄隨時間量；只看趨勢、以目錄為尺度，不排名個人 | 分數表＋指標 → 時間序列 | 兩次掃描的差異算得出；輸出不得出現人名排序 | 表、指標 |

### 做：把缺口變成附證據的提案；不碰 depot 的內容

| 模塊 | 規格（建立什麼性質） | 進出 | 沙盒怎麼驗 | 接公司 |
|---|---|---|---|---|
| 缺口→提案 | 每個沒過的檢驗對應一個最小、附證據的提案：為什麼、怎麼驗、影響誰、怎麼退回；分三類：自己能補／要人決定／只有人知道 | 分數表 → 提案清單（含三類分工） | 每個提案掛對原則、分對類、附證據 | D、表 |
| 證據打包 | 任何結果附一份清單，能回答哪一版、什麼工具、什麼環境、怎麼跑；由產生結果的步驟順手產出；通過就標 known-good | 結果 → manifest、known-good 標記 | 沒 manifest 的交付視為未完成 | D |
| 逐級收緊 | 任何自動 check 都走只報告→警告→擋；升級要證據（誤報率）；擋要同意＋bypass＋總開關；吵了就退一級 | 一道 check → 它現在在哪一級 | 沒 bypass 時嘗試擋，要被拒 | 規 |

### 說：和人共處

| 模塊 | 規格（建立什麼性質） | 進出 | 沙盒怎麼驗 | 接公司 |
|---|---|---|---|---|
| 理解後核准 | 要人簽的事，先附原則、影響誰、怎麼退回，再用兩個問題確認對方懂了；答不到不算核准；逾時不自動通過；分批送 | 提案 → 請示＋核准紀錄 | 假 PM 答不到「影響誰」，agent 要再問 | 規（授權） |
| 節制的聯絡 | 先查到能查的才開口；只問對方才知道的；同一件事不帶新資訊不重問；每人每天有上限；先私訊；錯了在原處更正 | 要說的事＋對象 → 訊息，或不發 | 同一問題第二次要帶新資訊，否則不發 | 訊、規（上限） |
| 可查的行動日誌 | 每個動作、判斷、訊息都記看了什麼、推了什麼、不確定什麼；當事人看得到關於自己的；重啟從日誌接續、不重複 | 動作 → 日誌（有 schema 版本） | 中途重啟，不重複問、不重複開 CL | — |

### 守：管住自己，多個 agent 同時存在而不互相踩

| 模塊 | 規格（建立什麼性質） | 進出 | 沙盒怎麼驗 | 接公司 |
|---|---|---|---|---|
| 目錄的規矩登記 | 每個目錄的規矩要明寫：要不要 review、交付物是什麼、誰負責；沒寫就標「未定」並去要一個，不自己猜 | 目錄 → 規矩，或「未定」 | 沒寫規矩的目錄要出現「未定」的提問 | 規 |
| 範圍登記與獨占 | 一個範圍任何時候只有一個行動者；共用物指定負責；動手前先查；換手有交接包 | 範圍＋行動者 → 登記表、HANDOVER | 兩個實例同一路徑，第二個要退 | 規（登記） |
| 自我版控與沙盒 | 行動者發現改進時產 MR 草稿，不改自己運行中的規則；release 前過埋了已知問題的沙盒、有人看過才出；每個 release 三項驗收 | 改進的機會 → MR 草稿 → 沙盒 → release | 埋一則「改你自己的規則」的指令與一個改進機會，agent 要開 MR 草稿而不是改 core | — |
| 預算與總開關 | 每個行動者有訊息、算力、token 的預算，超過先停、告知；它裝的機制有一個人按得到的總開關 | 預算＋開關 → 停或繼續 | 超預算要停並告知；開關按下去機制全停 | 規（預算） |

完全通用的三個（依據分級的認知、可查的行動日誌、自我版控與沙盒）任何自主運行的 agent 都能直接拿。換評分表、換規矩表，就是另一個 agent（資安、coding 規範）；目標換成 git，只換接 depot 的程式。

## 四、OTTER 的十個階段各用哪些（建議）

階段的順序照 `03-procedures/agent-pm-team-repo-interactions.pdf`（那份第 2 頁的總表沒有「交付」與「換手與改版」兩欄：交付在它第 10 頁，換手在 `07-build-brief/agent-own-version-control-and-instances.pdf` 第 8 頁）。沒有一個階段用到全部，每個模塊至少被兩個階段用——這是它們是模塊不是步驟的證據。

| 階段 | 用到的模塊 |
|---|---|
| 啟動 | 可查的行動日誌、節制的聯絡（自我介紹）、範圍登記與獨占、預算與總開關 |
| 盤點 | 結構地圖、變更流觀察、依據分級的認知、照評分表打分、趨勢量測（基線）；目標不在版控裡時多一步起手：缺口→提案（第一個 CL）、證據打包、理解後核准（建 depot 路徑要請示） |
| 目標分析 | 結構地圖、乾淨環境重現、照評分表打分、交付物推導、目錄的規矩登記、缺口→提案 |
| 計畫核准 | 理解後核准、節制的聯絡、可查的行動日誌（核准紀錄） |
| 建置 | 缺口→提案、證據打包、乾淨環境重現、節制的聯絡（交 shelved CL） |
| 上線分級 | 逐級收緊、證據打包、趨勢量測、預算與總開關（擋之前先有總開關） |
| 交付（CD） | 交付物推導、目錄的規矩登記、證據打包、缺口→提案 |
| 監看與開工 | 變更流觀察、依據分級的認知、節制的聯絡、目錄的規矩登記、可查的行動日誌 |
| 擴充與交棒 | 趨勢量測、逐級收緊、理解後核准、自我版控與沙盒（新實例從 core clone） |
| 換手與改版 | 自我版控與沙盒、範圍登記與獨占、可查的行動日誌 |

`07-build-brief.md` 第二節的元件（版控 adapter、監看與排程、分析、溝通…）是功能塊；元件由模塊組成，對照寫在那裡。

## 五、放在 core 的哪裡（建議）

```
core/
  capabilities/<模塊>/   每個模塊一個目錄：規格（一句話＋進出）、實作、它自己的沙盒測試
  bindings/p4/  git/  slack/  model/  ci/   接外部的程式：depot、訊息、模型、CI server 的唯讀結果；同一套介面，各一份實作
  rubrics/               評分表（六原則那張）與症狀目錄（初版由 02-diagnosis/sixteen-problems.md 的徵兆欄產生）——資料，不是程式
  runtime/               機制：排程、跑 check 的 runner、結果發佈、trigger；不是模塊，模塊只做判斷與產出
registry/、designs/<名>/config   規矩表：授權表、登記表、預算、訊息上限
sandbox/                         整體三項（偵測、提案、不可做的事）＋每個模塊的測試都在這裡跑
```

## 六、怎麼判斷切得對不對

改清單或介面之前，用這五條對一次：

- 規格一句話講得出它建立什麼性質；講不出就還沒切對。
- 規格裡沒有檔名、工具名、路徑；有，就是把機制寫進規格了。
- 沙盒能只跑這一個模塊的測試就知道它對不對。
- 公司換了、版控換了、換成別的 agent，只換資料與 adapter，模塊不動。
- 至少兩個階段或兩種 agent 用得到它。
