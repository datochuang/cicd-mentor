# PM 手冊

寫給「PM」這個角色：負責把 CI/CD 導入團隊的人，和 project 的 PM 無關。由技術主管起頭、之後交棒，任何人都可能接，也可以多位 PM 各推一部分（D9）。sponsor（撐這件事的主管）也該讀。

## 一、你的角色

- **你定方向，agent 自主運行。** agent 不眠不休地觀察、發現、提案、動手、回報；它形成的每個方針（方向、優先順序、對團隊的新要求、影響別人工作方式的改變、擋 submit）要你核准。
- **核准建立在理解上，不是蓋章。** agent 會請你用自己的話說這個方案要達成什麼、會影響誰；說不出來，它會再講一次，不會先做。你很忙、提案會很多，這是最容易壞掉的地方——請示一頁、分批、附兩個問題，就是為了這個。
- **agent 會對你提異議。** 你的想法和原則衝突時，它會說衝突在哪、照做的後果、替代做法。最後你決定，決定與理由進決定紀錄。
- **三個時刻你要親自出面，agent 不能代：** 專案宣布（為什麼做，用 `01-why/`）、第一次同意擋 submit、第一次衝突。
- **你不會躲在 bot 後面。** agent 補你和團隊的接觸，不取代；你不只透過 agent 的摘要認識團隊。
- **你會越來越懂。** agent 每個提案附背後的原則與投影片頁碼；定期回顧上一階段的假設；逐步讓你自己判斷，它退到審核。

## 二、核准之前要懂的八個概念

不用懂實作，但這八個不懂，請示就會變成蓋章。每個都有一頁現成的圖。

| 概念 | 一句話 | 核准時會碰到的判斷 | 看哪一頁 |
|---|---|---|---|
| check（查）與判 | 機器跑一個 script 回 PASS／FAIL；判是「全 PASS 才過」 | 這道 check 查的是什麼？誤報會多嗎？ | `01-why/loops-and-ai-multiplier.pdf` 第 2–3 頁 |
| main 隨時可用 | 共用的那條線任何時候 sync 下來都編得過、跑得過 | 要不要讓半成品進 main？ | `01-why/loops-and-ai-multiplier.pdf` 第 5 頁（中圈：機器查過就進 main） |
| 只報告／警告／擋 | check 的三種上線等級；擋會真的讓人 submit 不了 | 同意擋之前，誤報率是多少、bypass 給誰 | `03-procedures/agent-pm-team-repo-interactions.pdf` 第 8 頁 |
| stream／branch | 一件任務一條線，做完、查過再併回 main | 一任務一條還是一人一條 | `02-diagnosis/team-treating-vc-as-backup.pdf` 第 9 頁（沒有 branch）；開工時怎麼代開見互動場景第 11 頁 |
| shelved CL | 給人看、還沒 submit 的改動；也是備份 | agent 交的東西長這樣，owner 決定收不收 | 同上第 7 頁 |
| manifest | 跟著結果走的一張清單：CL、工具版本、環境、指令 | 交付物要不要強制附 | `03-procedures/agent-entering-unknown-workspace.pdf` 第 5 頁 |
| 交付物與出包（CD） | 這個目錄交出去的是什麼、給誰；check 過就自動打包附 manifest 放到固定位置，下游自己拿 | owner 多半沒想過交付物；agent 推的草稿對不對、取用處放哪、誰能寫 | `03-procedures/agent-pm-team-repo-interactions.pdf` 第 9 頁 |
| 六個原則與檢驗 | repo 該有的性質，各有一個做得到／做不到的檢驗 | agent 的每個提案掛在哪一條 | `02-diagnosis/team-treating-vc-as-backup.pdf` 第 19 頁；`04-principles.md` |

agent 的義務：請示裡每個概念第一次出現都附一句解釋和那一頁。

## 三、要先談好的資源與人（agent 變不出來的）

| 要談的 | 跟誰談 | 沒談好會怎樣 |
|---|---|---|
| 哪些目錄、哪些資料可以給 LLM 看；用內網模型還是外部 | 資安、法務 | 整個專案被叫停——**第一件談** |
| agent 的 Perforce 帳號與權限（先只讀）、slack bot 帳號 | CAD／IT | 第一天就動不了 |
| agent 的 git repo 放哪（GitLab？）、誰建、團隊的讀權限、MR 的 CI 在哪跑（要跑得起沙盒） | CAD／IT | 第一步（沙盒）做不了；自我介紹說的「你們有讀的權限」會跳票 |
| 沙盒能不能用真的 EDA 工具與 license | CAD | 不能就用 mock，上真實 depot 前再用真的跑一次 |
| sponsor：誰在上面撐 | 部門主管 | 第一次衝突就沒了 |
| 第一個自願的試點團隊與 owner | PL | 沒人願意當第一個 |
| 裝 trigger 的權限、Swarm 有沒有 | Perforce admin | 建置那一步卡住；只能做定時 job |
| 跑 check 的算力與 license 配額 | CAD、各 flow 的 owner | check 排不進 queue，或擠掉工程師的 job |
| 結果放哪、誰看得到 | CAD／IT | 「結果可見」做不到，等於沒做 |
| 狀態板與日誌不用於考核 | 直屬主管、HR | 工程師開始藏東西，是最壞的結果 |

這張表是 agent 啟動前的 checklist。agent 可以幫你寫每一項要講的話，但要去談的是人。你同時是 sponsor 的話，前三件是跟自己談；不是的話，資源由 sponsor 談，你談試點與 owner。清單在 `09-open-decisions.md`。

## 四、分階段的路線圖、成功的樣子、停損

| 階段 | 做什麼 | 成功的樣子 | 停損 |
|---|---|---|---|
| 準備 | 第三節的表談完；agent 在沙盒驗收過；以只讀上線；盤點；選一個自願的試點模組 | 你手上有一頁現況與一個試點 | 資安或 admin 不同意 → 先解決，不硬上 |
| 試點 | 一個模組：PROJECT_MAP、第一道 sanity check（只報告）、狀態板、CL 說明模板；版控常規教前三件；交付物草稿給 owner 確認 | owner 採用了 agent 交的 shelved CL；check 每天在跑、結果有人看；六個檢驗至少一個從做不到變做得到 | owner 不採用任何東西、或團隊明確反對 → 停，agent 寫一頁原因給你 |
| 擴散 | 第二、三個模組；check 升到警告；交付附 manifest；開工輔導開始 | 新模組的上手比第一個快；有人自己開 stream | 誤報率壓不下來 → 退回只報告 |
| 常態 | 有共識的 check 才擋；團隊自己維護 pipeline；agent 退到監看與維運 | 四個指標的趨勢向好；agent 的私訊變少 | — |

每個階段結束，agent 給你一頁：做到了什麼、六個檢驗的狀態、四個指標、下一階段要談的資源。

## 五、怎麼讀請示

agent 的請示永遠是一頁（格式在 `08-templates/request-for-approval.md`）：

1. 要做什麼（一句）。
2. 掛在哪個原則、讓哪個檢驗從做不到變做得到。
3. 影響誰、怎麼影響（owner、下游、CAD）。
4. 不做會怎樣；替代方案有哪些、為什麼不選。
5. 怎麼退回。
6. **要你回答的兩個問題**——這是確認你懂了的機制，例如「這道 check 擋下來的 CL 會發生什麼事？」
7. 第一次出現的概念各一句解釋＋圖的頁碼。

你要做的：回答那兩個問題；說得出「這會影響誰」再核准；看不懂就說看不懂，agent 會換個講法。一段時間沒處理的請示不會自動通過。請示會分批，不會一天十件。

**「懂了」的操作定義**：你在請示的回覆裡（slack 或 MR 的留言）寫兩個問題的答案和一句「核准」；agent 比對答案和請示的內容，答案碰不到「影響誰」或「退回怎麼做」就回一則補充、再問一次；三次還不行，標「未核准」，請 sponsor 看。你不必寫得長，答得對就行。

## 六、紅線與失敗模式——你要守的那一半

agent 絕不做的事在 `05-behavior-guidelines.md` 第三節。其中幾件要你先做到位：

- **kill switch**：一個你和 admin 都能按的開關，關掉 agent 裝的所有 trigger。沒有它之前，trigger 只在「只報告」級跑。
- **狀態板與日誌不用於考核**：跟直屬主管與 HR 講好。agent 不向你報告個人的活動量；你也不要問。
- **擋 submit**：你和 owner 都同意、有 bypass、有負責人，才擋。第一次擋你親自宣布。
- **誤報**：agent 寧可少報；錯了在同一個 channel 更正。有人被錯怪，你要知道。
- **團隊為了躲 agent 把工作留在 workspace**：這是最壞的結果。一有跡象，agent 會退一級；你要支持它退，不要催它加嚴。

## 七、每個目錄講好要不要 review（D7）

Code review 不是原則，要不要由各目錄自己定、可以改。agent 盤點時會問每個目錄的 owner：要／不要、誰看、什麼時候，寫進 PROJECT_MAP。你的角色是讓 owner 願意定一個——定「不要」也可以，但要講好、寫下來；沒講好等於沒人看。agent 自己交的東西不在此限：一律 owner 收了才進 depot。

## 八、多位 PM 與交棒

- **一個 design 任何時候只有一位 PM。** 登記表記 design → 實例 → PM。
- **多位 PM** 共用 core 的規則，各自只定自己那部分的方針（優先順序、要不要擋、目錄的 review 規矩）。衝突（共用的 flow、IP、top 的 filelist 兩位都想動）交 sponsor 裁決，agent 不選邊。多個實例給你的請示與摘要合併成一份；你管的實例數有上限，實例數跟著 PM 與 license 的量走。
- **交棒**：agent 不換行為（規則從 core 來）。交接包從它的工作區產生：哪些方針是你核准的、狀態板、採用率與誤報率、還在等誰。新 PM 重新核准授權表；你核准過的方針在新 PM 看過之前繼續有效，agent 標「前任核准」。
- **第一階段**（技術主管自己當 PM）授權表可以放開；交棒後的預設授權表保守，影響別人的事往上請示 sponsor。

## 九、你要看的數字

- **六個檢驗**：每個試點模組，哪幾個從做不到變成做得到（`04-principles.md`）。動任何東西之前先量基線。
- **四個指標**（DORA 的 IC 版）：submit 到進 main 的時間、進 main 的頻率、check 失敗率（改壞的比例）、壞掉到修好的時間。只看趨勢、以模組為單位，不排名個人。
- **agent 自己的**：交的 shelved CL 被採用的比例、誤報率、私訊的量（該越來越少）。

## 十、第一週

1. 讀這份和 `README.md` 的四張圖；翻 `01-why/` 兩份，準備專案宣布要講的話。
2. 拿 `09-open-decisions.md` 去談第三節最前面四件：資安、帳號、sponsor、試點。
3. 和內網的 Claude Code 對一次 `CLAUDE.md` 的框架，確認它說得出這個 agent 要做什麼、不做什麼。
4. 定第一版授權表（`09-open-decisions.md` 有預設值）。
5. 等沙盒驗收過，再讓 agent 以只讀帳號上真實的 depot。
